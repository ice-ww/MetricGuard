# MetricGuard P0 核心诊断规格

后续变更：Issue #23 替代历史的全任务两轮澄清限制，当前规则见 [F1 交互契约](f1-interaction.md)。原 P0 冻结验收不代表后续代码已通过验收。

状态：规格及测试边界已于 2026-10-12 经用户确认。依据：已确认的 P0 设计契约、领域术语与 ADR，以及 SQL 安全、二元指标统计、LangGraph 状态与预算三份研究报告。技术验证均未运行；本规格不将研究建议视为已验证保证。

## Problem Statement

短视频增长分析中，总体指标可能掩盖分群恶化，新增增长可能来自低留存渠道，观测下降也可能由采集异常造成。只生成一段解释无法证明使用了正确口径、查询了足够证据或适时停止；单纯引用查询结果也无法排除分母、关联和去重错误。

项目需要一个可在本地重复运行、能够解释成功与失败的受控诊断闭环，并通过独立答案与非迭代基线检验其价值。求职交付应能说明核心机制和限制，不以代码量、工具数量或预设胜出结果作为完成标准。

## Solution

提供单人本地运行的分析任务入口，针对项目生成的合成快照解析问题、确定指标与窗口、按证据选择查询与统计步骤，最后输出事实、候选解释、支持与反对证据、未排除因素和受控图表。用户可查询任务状态、回答澄清、查看报告与 Trace，并运行冻结评测。

P0 先完成四类核心异常、24 个冻结任务与独立安全套件。输出是有证据的诊断，不承诺证明因果；允许正确说明证据不足、不支持或未发现足够异常证据。八类异常、约 40 个任务、完整前端和一键交付包装属于后续阶段。

## User Stories

1. 作为本地分析者，我希望提交自然语言问题与合成快照，以便启动一次可追踪的诊断。
2. 作为本地分析者，我希望看到采用的指标定义、分母和比较窗口，以便理解报告口径。
3. 作为本地分析者，我希望明确的名称和别名能直接匹配指标，以便减少不必要的追问。
4. 作为本地分析者，我希望真正的业务歧义触发澄清，以便避免系统擅自选择含义。
5. 作为本地分析者，我希望不支持的问题获得明确说明，以便避免无效追问。
6. 作为本地分析者，我希望数据不完整时得到限制说明，以便不会把缺失当成零。
7. 作为本地分析者，我希望留存使用成熟注册用户群，以便避免未成熟日期拉低结果。
8. 作为本地分析者，我希望系统识别新版本崩溃与留存下降的关联，以便定位需要进一步调查的版本。
9. 作为本地分析者，我希望同时看到渠道增长、留存与两类成本，以便区分数量增长和渠道质量。
10. 作为本地分析者，我希望完播事件与独立遥测被交叉核对，以便区分采集问题与真实行为变化。
11. 作为本地分析者，我希望看到分群表现及基期结构标准化结果，以便理解总体稳定是否掩盖恶化。
12. 作为本地分析者，我希望事实能定位到结构化证据，以便复核数字。
13. 作为本地分析者，我希望推断展示支持、反对证据和未排除因素，以便理解结论边界。
14. 作为本地分析者，我希望图表只引用已有证据，以便图表与报告一致。
15. 作为本地分析者，我希望统计结果展示效应、样本量与适用限制，以便不把显著性误当因果。
16. 作为本地分析者，我希望正常数据不会被强行解释为异常，以便信任系统的停止判断。
17. 作为本地分析者，我希望样本或证据不足时保留已知事实，以便仍能获得有限但有用的结果。
18. 作为本地分析者，我希望工具失败后只进行有上限的修复，以便任务不会无限循环。
19. 作为本地分析者，我希望澄清后继续同一任务并保留累计消耗，以便追踪完整分析过程。
20. 作为本地分析者，我希望中断任务保留轨迹并能作为新任务重跑，以便故障可解释。
21. 作为本地分析者，我希望区分执行结束和诊断成功，以便正确理解预算耗尽或拒绝结果。
22. 作为本地分析者，我希望看到每次调用、错误、证据及消耗，以便定位失败环节。
23. 作为本地分析者，我希望越权请求不能读取快照之外的数据，以便保持本地数据边界。
24. 作为本地分析者，我希望失控查询被终止且服务仍可处理后续任务，以便单次失败不破坏系统。
25. 作为评测维护者，我希望黄金答案与诊断材料隔离，以便评测不泄漏答案。
26. 作为评测维护者，我希望不同数据实例而非仅换问法构成测试，以便检验诊断泛化。
27. 作为评测维护者，我希望参考查询独立于 Agent 查询，以便发现口径错误。
28. 作为评测维护者，我希望按结果与证据判分，以便允许不同但正确的分析路径。
29. 作为评测维护者，我希望三轮结果全部保留，以便判断稳定性而非挑选最好结果。
30. 作为评测维护者，我希望 Agent 与非迭代基线共享输入与权限，以便衡量迭代分析的实际收益。
31. 作为评测维护者，我希望前置失败、错误降级和未知用量被如实记录，以便避免虚高通过率或虚低成本。
32. 作为项目维护者，我希望未实测能力先通过明确验证门，以便实施不会建立在未经验证的假设上。

## Implementation Decisions

### 已确认的范围与模块职责

- 单 Agent 受控状态图；保留指标检索、白名单 Schema、标准化维度画像、只读关系查询、确定性统计和证据图表六项能力，不要求全部作为 Agent 自主调用工具。
- DuckDB 保存分析快照；SQLite 保存任务、澄清、Trace 等运行元数据，Agent 无 SQLite 查询权限。
- 分析任务服务提供创建、查询状态、提交澄清、读取报告与 Trace 的能力；评测入口提供运行及读取结果的能力。P0 通过命令行或 API 完成端到端验证，不依赖完整 UI。
- 用户输入、模型输出和检索数据均不得直接修改权限、预算或系统路由；程序验证动作和参数，执行后保存证据。
- 报告有足够支持、没有可继续检验的解释、证据不足、预算耗尽或越权时停止；不要求强行归因。
- 14 天为第一版目标，范围可延期，已确认安全与证据标准不降低。

### 数据与指标契约

快照保留用户、会话、内容事件、渠道日汇总和发布日历等业务关系，并允许补充独立播放遥测；不以五张表为硬限制。用户、会话、播放实例和事件必须有可验证的关联与去重规则。实际字段在前置验证中固定。

新增用户自然日次日留存：以 Asia/Shanghai 划分自然日，分母为 D 日首次注册用户，分子为其中 D+1 至少产生一次会话的用户；只纳入次日完整且数据齐备的用户群。渠道、系统和版本固定于注册时。

有效播放率为达到 min(5 秒, 视频时长) 的播放次数占播放开始次数；完播率为完成播放次数占播放开始次数。两者不可混用。每新增用户成本和每次日留存用户成本使用同一渠道、注册窗口的支出及相应人数；零分母不可计算。

每个数据源显式声明完整截止时间；默认比较最近七个成熟注册日与紧邻的前七日，以快照而非机器当前日期确定。用户日期优先，范围不完整则提示、缩小可比较范围或说明无法比较，不静默补零。

| 场景 | 必须支持的分析结果 |
| --- | --- |
| A1 新版本崩溃与留存下降 | 验证变化，定位 Android 与注册版本，核对发布日历及首日崩溃受影响比例，检查旧版本/iOS 对照；实际崩溃版本与注册版本分开记录，实例不模拟观察期升级，不声称证明因果 |
| A2 低留存渠道拉动新增增长 | 定位新增贡献渠道，展示新增占比、次日留存、每新增用户成本及每次日留存用户成本，不称为用户造假，不额外引入激活口径 |
| A3 完播事件缺失 | 通过唯一 play_id 对齐开始、完成事件与独立遥测，去重上报、区分重复观看；两链路齐备后判断缺失，无法对齐或无独立证据则保留不确定性 |
| A4 用户结构变化掩盖分群恶化 | 展示系统留存与新增占比，用基期系统占比加权本期留存，与实际总体对照，不泛称辛普森悖论 |

每个 P0 异常实例只注入一种机制，保留正常波动及对照分群。无异常与证据不足另设实例。异常编号、注入参数、黄金答案和预设路径不得进入 Agent 可见材料。

### 检索、证据与统计

精确指标名或别名优先，BM25 补充并返回 Top 3；阈值与候选分差由开发集校准，不能按验收题调整。

证据包含工具及参数、结构化结果与字段类型、来源/执行查询、快照标识、时间与分群、样本信息、限制、截断状态及稳定证据标识。摘要不能替代实际结果。事实断言绑定指标、分群、窗口、比较对象、数值和结果位置；推断引用相关事实并检查反对证据。引用覆盖率与断言校验通过率分别报告。

缺少有效支持的断言被删除、降级或使案例失败，过滤和降级必须留痕；空报告不能通过。图表只引用已有证据，不能自行补数据。截断结果不支持完整排名或总体占比，除非查询已正确计算完整总体。

P0 统计限定用户级二元指标，展示差值、样本量与区间；方法不适用时保留可核验描述，不强行检验。业务阈值、精度及数据充分性规则先校准后冻结，自适应下钻保留探索性限制。

### 状态、恢复与初始预算

执行状态：排队、运行、等待澄清、已结束、执行失败、中断。分析结果另分有支持的诊断、未发现足够异常证据、证据不足、不支持、拒绝越权、预算耗尽。

澄清沿用任务及累计预算；服务重启把原运行中任务标为中断，保留轨迹，不自动任意续跑；重跑创建新任务并关联旧任务。图结束不等于诊断成功。

| 约束 | 初始配置 |
| --- | --- |
| 诊断工具调用 | 12 次，检索、Schema 和失败调用均计入 |
| SQL 修复 | 初次执行加最多两次修复，共三次，每次计入工具预算 |
| SQL 时间及结果行数 | 5 秒、1,000 行 |
| 任务活动时间 | 180 秒，用户等待不计入 |
| 模型调用及 Token | 10 次；累计输入输出采用 30,000 Token 调度保护值，覆盖规划、修复与报告 |
| 澄清及图表 | 最多两轮澄清、三张图表；图表后处理不占诊断工具预算 |

预算由程序强制执行，模型不能重置。为报告预留额度，不足时以确定性模板返回部分结果。费用如实记录，未知用量不记为零。上述数值是待校准初值，不是性能或严格实时保证；验收前冻结。

2026-10-13 用户确认：30,000 Token 是调度保护值，不承诺提供方实际用量硬上限。调用前原子检查已知实际用量、未结算预留、本次完整输入估值加最大输出，以及报告余量；不足则拒绝发送。输入覆盖系统、工具 Schema、历史和共享材料，当前估值为完整序列化请求 UTF-8 字节数，不是 Token 上界。额外保留 1024 估值额度和一次报告调用；报告本身仍需完整准入检查，额度不足时由后续任务集成使用确定性模板。已知 usage 如实登记，即使超过估值或保护值也不截断；达到或超过保护值后拒绝新模型调用。未知 usage 保留预留、费用记未知，并阻止同任务后续模型调用（包括模型报告），跨重启不解除。详见 [T07 收口报告](../validation/t07-scheduler-closure.md)。

### 基线及评测执行

非迭代基线一次生成整批查询，经过相同安全层执行，再用一次模型调用生成报告，不根据结果补查或修复。双方使用同一模型、问题、快照、初始指标定义与 Schema，相同查询尝试、时间和 Token 调度保护规则及估值方法，记录实际消耗。

共享材料由同一前置流程生成，不读取答案；主对比从材料准备完成后计时，前置成本单列，材料输入 Token 分别计费。前置失败单列但不静默剔除；端到端评测仍计全部前置调用。是否优于基线是实验结果，不是必须造出的成功条件。

## Testing Decisions

### 已确认的测试边界

**一个主要业务边界：分析任务服务的公开行为。** 测试从提交问题、查询状态、回答澄清、获取报告与 Trace 出发，断言可观察结果及持久化恢复行为；不依赖内部节点名称、执行顺序、私有方法或 Prompt 原文。确定性测试可在模型提供方边界注入受控响应；冻结评测必须使用真实锁定模型。

仅补充三个具有独立责任的验证边界，避免把每个内部函数都变成测试耦合点：

1. **受限查询执行器**：真实引擎与隔离环境下验证权限、资源、结果及回收；不仅验证 AST 抛错。
2. **统计计算接口**：固定计数、口径元数据与适用条件，对照独立参考结果，验证边界及拒绝行为。
3. **评测运行器**：给定冻结任务与模型配置，核对计分、失败分类、三轮汇总及基线记账，防止错误归因或隐藏失败。

独立调用账本通过任务服务的故障注入与状态观察验证，不另建对每个 reducer 或节点的镜像测试。数据参考查询用于构建可信夹具及判分依据，不能复用被测实现。

当前仓库只有技能与设计研究文档，没有产品代码、既有公共接口或测试套件可复用；以上边界是本规格提出的新边界。

固定模型配置、Prompt、快照、任务和规则版本，连续运行三轮；每轮均满足：简单查询 6/6；核心完整通过至少 9/12 且每类至少一个；其余六个行为任务全部通过；独立安全套件全部通过；发布的事实与推断均有引用，结构化事实断言均通过校验。早期对候选解释保留人工复核，人工判断和结果留档。

分别报告注入异常归因命中率、完整案例通过率、SQL 数值/口径正确性、引用覆盖率、断言校验通过率、安全结果、失败类型及被拦截/降级的错误；保留全部三轮，不挑最好一轮。记录活动耗时及 P50/P95、步骤数、模型调用、Token、费用或未知费用，说明计时边界。

冻结集用于定向修复后标记为回归集，不再称未见测试集；失败不得通过删题、改答案或临时改阈值消除。

## Out of Scope

- 真实业务数据库、任意数据上传、公开在线服务、多用户与分布式调度。
- 多 Agent、Embedding/向量数据库、Kubernetes、多个业务分析数据库、模型微调。
- 任意 Python/Shell 执行、业务数据自动修改、无边界 SQL。
- 同时注入多个异常、观察期跨版本升级、独立激活漏斗、两均值检验及不受支持的配对/聚类推断。
- 证明现实因果、把探索性区间解释为最终诊断的 95% 可靠性、要求 Agent 必然优于基线。
- 任意节点崩溃后自动续跑、未知远端调用结果的 exactly-once 承诺。
- A5 至 A8、约 40 任务扩展、完整 React 页面、独立评测 UI、SSE/WebSocket、美化和完整一键发布包装。
- 本次规格工作不运行上述验证，不实现产品代码。

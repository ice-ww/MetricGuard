# MetricGuard P0 设计契约

本契约汇总设计访谈中确认的 P0 规则，整体设计已于 2026-10-12 经用户确认，设计访谈结束。后续工作为技术验证和实施规划；设计确认不代表技术验证已通过，尚未开始产品实现。术语以根目录 GLOSSARY.md 为准，架构取舍见 docs/adr/。

## 产品与交付边界

MetricGuard 是面向短视频增长指标的单 Agent 受控诊断项目，输出观察事实、候选解释、支持与反对证据和未排除因素，不承诺从观测数据证明因果关系。
P0 面向单人本地运行，仅分析项目生成的合成快照，不接入真实业务数据库，不接受任意数据文件上传。公开交付指代码仓库、评测结果与演示视频；在线托管另立阶段。

14 天为第一版目标，优先交付可信的四类核心异常闭环；八类异常、约 40 个任务与完整前端允许延期，安全和证据标准不降低。
保留单 Agent 受控状态图、BM25、只读分析、证据验证、最小 Trace 及命令行或 API 端到端运行；原方案六项能力仍保留，但可调用工具数量不作为硬性指标。
图表生成暂列为报告后的确定性步骤候选，具体接口通过技术验证确定。继续排除向量数据库、多 Agent、Kubernetes、任意代码执行、自动修改业务数据与模型微调。

## 工作流约束

沿用解析问题、获取指标定义与 Schema、规划、受控工具循环、证据校验、报告与图表的主流程。指标歧义先澄清，工具权限和预算由程序检查；每次执行保留证据并更新候选解释，允许根据结果补查或有限修复。
诊断有充分支持、没有可继续检验的解释、证据不足、预算耗尽或出现越权请求时进入相应结束分支；不将“完成根因验证”作为声称已证明因果的终止条件。具体 LangGraph 节点与状态字段在实施规划中展开。

## 核心场景

- A1 主证据为注册当日至少发生一次崩溃的新增用户数除以当日新增用户数；会话级崩溃率为辅助指标。记录崩溃实际发生时的系统和版本，留存按注册版本归组；P0 的 A1 实例不模拟观察期内跨版本升级。
- A2 为低留存渠道拉动新增增长：展示渠道新增占比、次日留存率、每新增用户成本和每次日留存用户成本，成本分母为零时不可计算；P0 暂不引入独立激活口径。
- A3 的播放开始、完成事件和独立观看进度通过唯一 play_id 关联；同一次播放的重复上报去重，重复观看使用新的 play_id。只有两条链路都已超过完整截止时间才判断完成事件缺失；不能对齐的数据标记为质量限制，不强行归因。
- A4 固定使用新增用户自然日次日留存：展示各系统留存率、新增用户占比，以及基期结构标准化留存率，与实际总体留存比较。

## 统计能力

P0 聚焦留存等用户级二元指标。满足比较条件时输出差值、样本量和置信区间；条件不满足时明确标记，统计显著性不单独决定异常或因果判断。
探索中尝试过的比较全部保留在 Trace；两均值检验延期，直到明确重复播放和重复会话的统计单位。具体检验条件与置信区间方法仍待确定。

为核心指标预先定义业务变化阈值和数据充分性条件，在开发阶段使用正常波动与异常实例校准，验收前冻结。区分没有达到预设异常标准与数据不足以判断，不能按验收题临时调整阈值。

## 指标检索

精确名称或别名匹配优先，BM25 补充检索并保留 Top 3；BM25 阈值和候选分差使用开发查询集校准。
业务歧义需要澄清，例如未说明人群的留存问题；语料不支持的问题直接说明不支持，避免反复追问。

## 任务持久化与恢复

DuckDB 保存业务分析数据，SQLite 仅保存任务、澄清和 Trace 等运行元数据，Agent 无 SQLite 查询权限。
P0 支持 SQL 有限重试与澄清后继续。服务中途重启时，运行中任务标记为中断，保留轨迹并允许重新运行；不承诺从任意节点自动续跑。
SQL 重试和工具调用预算遵循 ADR 0008，其余初始预算见下文。

执行状态分为排队、运行、等待澄清、已结束、执行失败和中断。分析结果另行区分有支持的诊断、未发现足够异常证据、证据不足、不支持、拒绝越权和预算耗尽；报告生成成功不自动代表诊断成功。
澄清后沿用原任务及累计预算；重新运行创建新任务并关联旧任务。

## 比较窗口

每个数据快照显式声明各数据源的完整截止时间。默认比较最近七个已成熟注册日与紧邻的前七日，展示实际日期；窗口相对于数据快照确定，而非运行机器的当前日期。
相关数据源不齐备时缩小可比较范围或说明无法比较，不静默补零；用户指定日期优先，但窗口不完整时明确提示。

## 计分与验收门

按结果与证据评分，不要求固定工具调用路径。核心案例通过需同时满足解释命中、定位正确、关键指标与比较正确、证据有效、未越过因果表述边界。
每个案例事先定义必需断言、数值容差及禁止结论；分别报告归因命中率与完整案例通过率，空报告不能因没有错误断言而通过。

数值一致性与口径正确性分开验证：运行时核对结果引用及指标、时间、分群等信息；评测时使用独立编写并人工核对的参考查询验证关键结果，避免复用 Agent 的计算逻辑。
自由查询不能仅因数字与引用结果一致就宣称业务口径正确；关联重复、分母错误与遗漏过滤条件都属于应识别的口径错误。

固定模型配置、Prompt、数据快照和任务集，连续运行三轮并全部报告。每轮均需满足：

- 简单查询 6/6 正确。
- 核心案例完整通过至少 9/12，且 A1 至 A4 每类至少通过一个案例。
- 无异常、证据不足、歧义澄清和工具恢复任务全部通过。
- 独立安全套件全部通过。
- 最终发布的事实与推断均有引用，结构化事实断言均通过校验。

同时记录被拦截或降级的错误，避免过滤后的报告掩盖生成失败；三轮结果不得挑选最好的一轮代替全部结果。

## 初始预算

以下为可配置试运行值，在开发集校准后冻结用于验收，不表示已经满足性能目标：

- 每次 SQL 最长 5 秒，最多返回 1,000 行。
- 每任务累计活动执行时间最多 180 秒，等待用户澄清的时间不计入。
- 模型调用最多 10 次，累计输入与输出最多 30,000 Token，覆盖解析、规划、修复和最终报告。
- 最多两轮澄清，图表最多三张。
- 为最终报告预留预算；不足时用确定性模板返回部分结果。
- 记录实际费用，暂不设置依赖具体模型价格的金额门槛。

## 非迭代基线对比

主对比给 Agent 与基线完全相同的初始指标定义和 Schema，固定同一模型、问题、数据快照与安全规则；基线一次性提交查询计划，Agent 可以根据结果继续下钻。
两边适用相同的查询尝试数、时间与 Token 上限，报告实际消耗。检索与澄清另做端到端验收，不混入迭代能力主对比。
共享材料由同一套前置流程生成，不读取黄金答案。主对比从材料准备完成后开始计时，前置耗时与成本单独列出；两边消费材料产生的输入 Token 各自计入预算。
前置失败任务单独报告，不静默剔除；完整端到端验收仍计入所有前置调用。

P0 是否通过由绝对验收标准决定，是否优于基线作为实验结果报告。逐任务展示双方成功、失败与成本；Agent 没有优势时说明迭代在哪些场景无收益或成本过高，不通过修改任务集制造胜出。

- LangGraph 节点与状态结构、五类诊断能力的工具契约及图表后处理接口。
- 模型与版本选择、调用和 Token 预算预留、共享前置材料的记账测试，以及开发集上的性能校准。

验收前冻结上述实现及规则的版本，技术验证失败时修正实现或如实收缩承诺，不更改验收题制造通过。

# T10 澄清、中断与重跑契约

后续变更：Issue #23 / F1 将下述历史“两轮”策略替换为每个未解决原因两次回答、全任务最多十二次回答；不同信息缺口可连续澄清。当前规则与终端说明见 [F1 交互契约](f1-interaction.md)。预算和重复提交防护不变。

`metricguard.TaskService` 在 T09 公开入口上增加 `answer(task, question_id, version, answer)` 和 `rerun(task)`，CLI 增加同名命令。其余入口与已发布 T09 请求格式保持兼容。

## 澄清与累计记录

检索结果需要澄清时，任务进入 `waiting`，分析结果仍为 `None`，报告未生成。程序保存问题 ID、版本、具体原因和提示；实际 LangGraph `interrupt` 节点只读取已保存问题并暂停，不执行调用或写入。用户答案通过独立节点应用，再重新检索；每次新检索占用新工具尝试，已保存的调用及账本不清空。

`answer` 同时核对待答问题 ID、版本、持久化 checkpoint interrupt 值，并以 SQLite 条件更新原子地将 `waiting` 改为 `running`。重复、过期或并发败选的答案不触发继续执行。每个任务最多两轮；两轮后仍无法确定口径则结束并明确证据不足。不支持的人群或周期直接结束为 `unsupported`，不会反复追问。

活动时间仅计执行分段，等待用户时停止累计，服务关闭再打开也不把等待时间记入活动预算。任务状态与分析结果分离，等待、中断和图结束均不意味着分析成功。

## 重启、重跑及兼容

服务使用单所有者锁。原 `running` 任务在重新取得所有权时标为 `interrupted`，未完成调用保留未知状态、记录和预留，不自动续跑。原 `waiting` 任务保持同一待答问题及 checkpoint，可通过合法答案继续。

`rerun` 只接受已结束、失败或中断任务，创建新任务并保存 `parent`。新任务继承原始问题、注册快照、用户请求窗口和已经明确的澄清上下文，保留来源关系；不继承原待答问题或累计预算。澄清后的有效文本可能超过单条输入 2,000 字符，因此重跑复制原始输入及已接受上下文，不再次把累计文本当成新用户单条输入验证。旧任务不被改写。

T09 已发布的 JSON 尚无 `answers`、`effective_question`、`pending_question`，读取时分别规范化为 `[]`、原问题、`None`。兼容测试构造旧持久化格式，再仅通过公开入口核对运行和重跑。

## 故障注入与重放验证

管理员可在构造时传 `fault_hook`；任务、答案、检索文本或模型输出均不能设置它。适配器在预留后与结果持久化后通知钩子；任务图在查询完成但 checkpoint 前和进入报告节点后通知钩子。真实发送中崩溃由实验 HTTP 提供方记录独立 durable marker 后退出进程。

这些钩子仅供实验，不增加生产自动重试策略、任意节点自动恢复或 SQL 修复。真实图侧通过 interrupt/resume 核验等待节点重放与累计记账；已完成模型调用另使用最终服务的持久化账本和原实际请求，经适配器公开 `call` 重放同一 attempt，验证无新发送、无重复计费。不能把这项有限验证扩展为任意生产图崩溃后的 exactly-once 保证。

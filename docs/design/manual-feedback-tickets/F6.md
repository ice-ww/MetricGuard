## Parent

Part of #22 — 手动验收反馈修复：时间口径、证据呈现与澄清体验。

## What to build

在集成版本重跑原失败场景并增加新的问法、日期与数据参数，完成真实运行、独立核查、完整回归和子代理审查，交付用户手动复验清单及报告。

## Acceptance criteria

- [ ] 保留原五份失败记录；通过修改后的公开服务重新执行场景，不能以静态旧记录审计作为修复通过依据。
- [ ] 新增问法、日期组合和数据参数，覆盖时间冲突→基期确认→范围选择→报告完整流程，包括跨日恢复及无可用范围。
- [ ] 使用真实模型和实际隔离查询，独立 SQL/Python 核对日期、人群、分子分母、数值及引用，不复用被测逻辑产生期望。
- [ ] 归档输入、任务 ID、确认过程、SQL、报告、原始证据、参考结果与版本标识；分别报告确定性测试、真实运行及人工体验结果。
- [ ] 运行类型检查、相关及完整回归测试；必要集成测试跳过不计通过。四类问题分别列出原失败、回归、新场景与核查结论。
- [ ] 子代理独立审查规格符合性与代码标准，解决确认的问题后复验；不得以机械校验有效替代语义正确。
- [ ] 交付可直接操作的终端复验清单，包含预期行为、证据定位和失败记录方式；用户体验验收未完成时明确标记待验，不由代理代签。
- [ ] 不使用未见冻结材料定向调优、不借旧正式验收证明新代码通过；不建设图形界面，不自动关闭父规格 Issue。

## 验证与范围

遵循父规格已确认的 TaskService 公开行为和必要终端验收边界，测试用户可观察行为，不耦合私有函数或 Prompt 原文。开发任务采用先失败后通过的回归测试，进行类型检查、适用的真实查询/模型验证和独立审查；保留证据及未通过项。核心业务规则由服务执行，沿用证据、隔离及预算边界。此任务不建设 Web/桌面交互界面。

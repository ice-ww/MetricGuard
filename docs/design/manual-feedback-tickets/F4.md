## What to build

完整性不足时说明缺少的数据、可用日期及补齐条件，用户授权后才缩小范围；重新核查比较条件，并限定结论适用范围。

## Acceptance criteria

- [ ] 根据指标所依赖的数据源完整性和成熟条件判断范围，次日留存检查 D+1 完整性，不能只看注册数据。
- [ ] 明确请求范围、可用范围、缺失日期、数据源或成熟条件及补齐条件；不把水位解释为预计更新时间。
- [ ] 存在可用范围时提供分析可用范围和保留原范围返回不足说明两个选择，支持自由输入；未经授权不缩短。
- [ ] 完全无可用日期时直接解释不足与下一步，不给无效选项；拒绝缩小不输出冒充完整窗口的局部诊断。
- [ ] 接受缩小后保留原请求与授权，报告开头展示原范围和确认范围，声明不能推广至原范围。
- [ ] 重新核查比较条件，进一步日期变更须明确确认；不足以比较时只返回已有事实及无法判断原因。
- [ ] 公开入口和终端覆盖完整、部分可用、完全不可用、基期不足、接受/拒绝缩小和连续澄清；独立参考核对成熟日与查询窗口。
- [ ] 同步替代旧自动缩窗契约，保留旧报告含义和历史失败记录；真实运行验证报告、授权与 SQL 一致。

## 验证与范围

遵循父规格已确认的 TaskService 公开行为和必要终端验收边界，测试用户可观察行为，不耦合私有函数或 Prompt 原文。开发任务采用先失败后通过的回归测试，进行类型检查、适用的真实查询/模型验证和独立审查；保留证据及未通过项。核心业务规则由服务执行，沿用证据、隔离及预算边界。此任务不建设 Web/桌面交互界面。

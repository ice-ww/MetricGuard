# 手动验收反馈修复：时间口径、证据呈现与澄清体验

状态：产品规则、整体约定与测试边界均已获用户确认。尚未实施或验收。

规格 Issue：[GitHub #22](https://github.com/ice-ww/MetricGuard/issues/22)，标签 `ready-for-agent`。

## Problem Statement

手动验收发现四类问题：自然语言时间与预设窗口冲突时未澄清，实际分析了一周而非用户所说的昨天；终端遗漏具体事实和引用，部分诊断正文自身也缺少对象及数值；证据不足说明未具体指出可用日期、缺口与下一步；澄清在已知日期时仍泛泛要求补充时间，并展示内部 JSON。

这些问题分别影响口径正确性、可核查性和使用体验。此前 P0 的固定案例验收不构成本轮新增交互行为已经正确的证据。

## Solution

建立一致的任务行为：先确定指标、分析日期和必要的比较基期，再检查数据充分性；需要缩小范围时由用户选择。报告提供具体对象、关键数值、直接引用及结论限制。终端展示这些信息，核心规则由任务服务执行，以供未来最小交互界面复用。

## User Stories

1. 作为分析者，我希望“昨天”使用任务创建时的业务日期，以便含义明确。
2. 作为分析者，我希望跨天回答澄清不会改变相对日期，以便任务语义稳定。
3. 作为分析者，我希望文本与预设日期冲突时看到两个具体范围，以便选择真实意图。
4. 作为分析者，我希望历史快照不会偷偷改变“昨天”的含义，以免分析错误日期。
5. 作为分析者，我希望能使用明确日期范围、昨天、前天、最近 N 天、本周和上周，以便方便表达时间。
6. 作为分析者，我希望含糊的时间表达触发澄清，以免系统猜测。
7. 作为分析者，我希望看到解释后的具体日期及边界，以便核对查询口径。
8. 作为分析者，我希望变化分析在缺少基期时提出前一个等长窗口供确认，以便比较依据明确。
9. 作为分析者，我希望已指定的基期不被替换或重复询问，以便保持控制。
10. 作为分析者，我希望简单数值查询不被迫确认无关的比较基期，以便减少操作。
11. 作为分析者，我希望知道哪些数据不足、哪些日期可用，以便理解分析限制。
12. 作为分析者，我希望自行选择是否缩小分析范围，以免局部结果替代完整请求。
13. 作为分析者，我希望没有可用范围时获得明确说明，而非无效选项，以便采取下一步行动。
14. 作为分析者，我希望缩小范围后的报告展示原范围与确认范围，以便理解结论边界。
15. 作为分析者，我希望比较条件不足时返回已有事实和无法判断的原因，以免把不足误认作正常。
16. 作为分析者，我希望主要判断直接列出具体系统、版本或渠道，以便知道分析对象。
17. 作为分析者，我希望看到关键数值和比较结果，以便理解判断的大小与方向。
18. 作为分析者，我希望每个关键事实都能追溯到证据位置，以便复核。
19. 作为分析者，我希望看到反对证据、未排除因素和因果限制，以免误解候选解释。
20. 作为分析者，我希望正文简明且另有完整事实表，以便兼顾阅读和审计。
21. 作为分析者，我希望澄清先展示已知信息、只问缺失项，以便避免重复输入。
22. 作为分析者，我希望可以选择建议答案或自由输入，以便表达例外需求。
23. 作为分析者，我希望回答后在同一任务中继续，并保留已确认信息，以便流程连续。
24. 作为维护者，我希望日志仍保留内部标识、原因和证据，而普通交互使用自然语言，以便兼顾排查与易用性。
25. 作为维护者，我希望原失败案例和新日期、新问法均参与验证，以便避免只适配已知例子。

## Implementation Decisions

### 时间与比较口径

- 业务时区使用 Asia/Shanghai，相对日期锚定任务创建时间并持久化；同一任务的等待、恢复不改变锚点。不得以快照日期替代真实时间锚点。
- 支持明确日期范围、“昨天”“前天”“最近 N 天”“本周”“上周”。最近 N 天为截至昨天的 N 个完整自然日；周一为周起点。周区间按自然周解释并展示日期，包含今天或未齐备日期时进入完整性检查，不将其默认为完整数据。
- 无法唯一解释的日期（如缺乏足够上下文的日期或“最近”）需要澄清；不凭空推断。窗口沿用起始日包含、结束日不包含的内部约定，用户展示明确可读的实际日期范围。
- 文本时间与预设窗口一致时无需冲突澄清；不一致时展示两者并等待选择。选择后实际查询必须遵循确认结果。
- 变化分析未明确基期时，建议前一个等长窗口，用户可以确认或修改。先解决分析窗口冲突，再确认基期；已有明确基期不重复询问。简单查询无需添加无关比较。
- 分析窗口或基期不完整时，不静默替换或缩短。

### 数据充分性与范围授权

- 以指标依赖的数据源完整性和成熟条件判定可用范围；次日留存不能把注册日有数据等同于次日观测完整。
- 说明请求范围、可用范围、缺少的数据源或成熟条件、缺失日期及补齐条件。完整截止日期不等于预计到达时间，不编造数据更新承诺。
- 存在可用范围时提供“分析可用范围”和“保留原范围，返回不足说明”，必须得到选择才能缩小范围；没有可用范围时直接说明不足和下一步。
- 缩小范围后保留原请求及用户授权，重新检查基期与比较条件，任何进一步变更不得隐含发生。报告明确结论仅适用于确认范围；不足以比较时只给已有事实及无法判断的原因。

### 报告与终端

- 主要判断包含实际对象名称、关键数值和证据引用；数值与对象来自已校验的结构化事实，不允许通过补写自由文本引入未经校验的事实。
- 展示百分比、人数和差值时保留正确单位与分母语义，不能混用百分比变化和百分点变化；显示取整不改变原始证据值。
- 简单查询直接回答数值；诊断展示比较依据、相关反对证据、未排除因素及因果限制。无反对证据不意味着不存在替代解释。
- 正文突出必要事实，完整事实表和原始证据可继续查阅。引用必须能定位具体事实及证据结果，不能仅显示无法追溯的编号。
- 终端与保存报告复用核心服务提供的事实和说明，避免只在本地操作脚本内修复业务规则。交付可版本控制、可重现的终端验收入口，不依赖某台机器上未跟踪脚本才具备正确行为。

### 澄清与兼容

- 面向用户展示已知信息、明确问题和可选答案，同时保留自由输入。内部任务标识、问题版本、原因代码保留在持久化状态和日志中。
- 日期冲突、基期确认、数据范围授权以及指标缺失可能形成连续阶段，合法流程不得因旧的全任务两轮上限被提前终止。仍需限制无效反复澄清，并给出明确停止原因；保留执行预算，不允许通过澄清重置预算。
- 保留重复答案、过期答案及并发提交防护；等待不计活动执行时间，恢复继续同一任务，旧任务与失败证据不可覆盖。
- 此规格明确替代旧契约中自动缩短请求窗口的行为，并要求调整固定两轮澄清限制。既有结构化证据、模型外安全与预算边界、业务数据和任务元数据分离的 ADR 继续有效。
- 旧任务的读取保持兼容；缺失新时间锚点或确认记录不能伪造为用户已确认。历史报告保持原始含义，新增任务遵守新契约。

## Testing Decisions

沿用已批准的主要测试边界：TaskService 的公开任务行为，包括提交、运行、状态查询、回答澄清、报告发布、Trace 与恢复。仅增加必要的终端入口验收，验证用户实际看见的内容，不建立私有函数或 Prompt 原文镜像测试。用户已明确回复“同意”，确认本轮测试边界。

- 沿用现有服务澄清和恢复测试的做法：可在模型提供方边界注入受控响应，实际查询使用隔离 DuckDB；固定时间、快照与随机种子，构造先失败后通过的回归测试。
- 验证日期冲突确实暂停、确认后 SQL 日期正确；覆盖跨午夜等待、月末/年末/周界、相同日期不重复询问、含糊日期、历史快照与当前日期不一致。
- 验证基期默认建议、用户修改、已明确基期、无关简单查询，以及日期冲突后才确认基期。
- 验证完整数据、部分可用、完全不可用、次日留存成熟性、基期不足、拒绝缩小与接受缩小；报告范围必须与实际查询和授权一致。
- 验证连续合法澄清不被旧两轮上限误杀，已知信息保留；重复/过期答案和恢复不重置预算、不改变日期语义。
- 验证诊断正文与终端确实展示对象、关键值、可追溯引用及限制。用独立 SQL/Python 参考核对日期、人群、分子分母和数值，不复用被测计算逻辑作为期望。
- 保留五份原手动验收失败记录及任务 ID。旧记录审计只能证明历史问题，不能证明新代码已修复；必须在修改后的服务上重新运行相应场景。
- 定向复验增加新问法、日期组合和数据参数，使用真实模型与实际隔离查询；保留输入、任务 ID、确认过程、实际 SQL、报告、引用及参考结果。分别报告确定性测试与真实运行结果，不把机械校验等同于语义正确。
- 实施完成后进行类型检查、相关测试和完整回归测试，交由子代理审查规格符合性及代码标准，再由用户完成简短体验复验。跳过的必要集成测试不计通过。
- 不将既有冻结验收结果宣称为新代码验收结果；开发与定向复验不使用未见冻结材料进行调优。

### 完成依据

四类问题均须具备原失败证据、运行新实现的回归结果、新场景实际运行记录和独立核查结论；终端可直接阅读和追溯关键判断。未通过项如实列明，不以无报错或报告机械有效替代行为验收。

## Out of Scope

- 本轮不建设 Web/桌面最小交互界面，不进行界面视觉设计。
- 不扩展任意自然语言时间、其他业务时区、新指标或新诊断机制。
- 不接入真实生产数据源，不承诺真实因果识别或数据自动补齐。
- 不重写全部历史报告，不追认旧记录已经用户授权。
- 不在本规格阶段实现代码、关闭 Issue 或声明新的正式冻结验收通过。

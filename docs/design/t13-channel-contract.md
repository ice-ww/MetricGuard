# T13 渠道数量、留存与成本

Issue #14 通过既有 `TaskService` 诊断接口增加 `channel_health` 业务画像：`table=users, column=channel`。模型依据问题及已有证据选择画像，没有异常编号、注入参数或固定 A2 路径。版本解释只读取自己的画像种类，渠道画像不会制造缺少版本崩溃证据的误报。

当前窗口沿用已成熟的注册窗口，比较期为前一个等长窗口。画像 SQL 在原有只读沙箱内执行；注册属性固定，D1 会话以 EXISTS 去重。同渠道、同注册窗口汇总支出，同时返回每新增成本与每留存成本（单位分）；零分母、缺失支出保留 null。仅有支出而无用户的渠道仍保留。渠道水位未覆盖当前窗口时拒绝画像，不把不完整支出与完整用户数拼接。

SQL 原始证据保留 period、channel、users、retained、retention_rate、spend_cents、两类成本和实际起止日期。受 512 AST 节点上限约束，程序在 `report.diagnosis.channel_metrics` 派生新增差值、总体差值、增长贡献与两期份额。`source_facts` 引用该渠道原始行，`total_source_facts` 引用完整总体；派生量明确标记 program_from_complete_channel_profile，不能伪称 SQL 原始单元格。净增长为零时贡献为 null，净增长为负只作有符号变化描述。

`channel-growth-v1` 在总体新增为正、该渠道新增为正，且该渠道留存比当前其他渠道按人数加权的留存低至少 5 个百分点时给出描述性候选。这个阈值是业务差值筛选，不是统计显著性。保留前后期原始事实、其他渠道对照、实际两类成本变化；不推断造假，不声称因果，不假定每新增成本必然上升。缺少对照渠道或支出会明确标记证据不足，未证明独立同质抽样，不发布置信区间。解释仍待人工语义复核。

公开验收边界为批准的 TaskService，受控模型只替换 HTTP 提供方，SQL 使用真实 Docker 执行器。数字以独立 Python 集合/循环参考核验。首个画像与成本完整性反例观察到 RED 后修复；零分母、净增长零、正常控制、缺成本及无渠道对照为回归反例，不能声称每个都单独观察过 RED。开发变体和真实模型实验由验收报告记录，未使用冻结验收集。
